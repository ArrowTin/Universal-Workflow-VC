# GIT STRATEGY

Git is the shared persistence and coordination boundary for multi-AI development.

## Before every task

```text
SYNC / PULL LATEST
→ inspect current branch/state
→ inspect TASK-LOG
→ verify ownership
→ verify affected files
```

Never assume the local repository is current.

## During a task

Work only within the claimed scope.

Do not overwrite or discard another AI's newer work.

Do not use destructive commands such as reset, force-push, or history rewriting against shared work without explicit coordination.

## Before commit

```text
SYNC
→ detect upstream changes
→ resolve safely
→ re-run affected verification
→ update logs
→ COMMIT
```

If upstream changes conflict with the task:

```text
STOP
→ inspect
→ preserve work
→ resolve
→ verify
→ commit
```

## Commit policy

* Completed task → commit.
* Material error fix → separate commit.
* Material documentation/state update → commit.
* Necessary checkpoint → explicit `WIP` commit.

Commit messages must identify the task, phase, or purpose.

## Phase policy

At phase completion:

```text
all tasks DONE
→ final SYNC
→ final verification
→ update PHASE-LOG
→ commit phase metadata
→ PUSH
```

A phase is not considered fully completed until its required push succeeds or the failure is explicitly recorded.

## Multi-AI safety

Never:

* overwrite another AI's work;
* force-push shared history;
* silently discard upstream commits;
* claim synchronization without actually synchronizing.

# EXECUTION

Layer 3 follows the project documentation generated by Layer 1.

## Runtime

```text
AGENTS.md
→ Phase / Task
→ SYNC
→ Ownership
→ Documentation
→ Skills
→ Memory
→ Context
→ Execute
→ Verify
→ Record
→ Commit
```

## Multi-AI execution

Before every task:

1. synchronize with the latest repository;
2. read the current task state;
3. verify ownership;
4. inspect dependencies and affected files;
5. claim the task;
6. load required context;
7. execute only within the task scope.

Independent tasks may execute concurrently.

Conflicting or uncertain tasks must wait.

## Synchronization

A repository synchronization is required:

* before starting a task;
* before integrating concurrent changes;
* before committing when concurrent work may have changed the branch;
* before phase completion.

## Skills

```text
Discover
→ Select
→ Load
→ Execute
→ Verify
→ Unload
```

Load only skills relevant to the task.

## Memory

Retrieve relevant project memory before execution.

Persist material discoveries, decisions, failures, and lessons that have future operational value.

## Model / agent switching

Models and agents may change dynamically.

Before switching, persist sufficient state for another AI to continue:

* task status;
* decisions;
* discoveries;
* unfinished work;
* verification status;
* relevant repository state.

## Completion

A task is complete only after:

```text
VERIFY
→ UPDATE TASK-LOG
→ COMMIT
→ mark DONE
```

A phase is complete only after:

```text
ALL TASKS DONE
→ FINAL SYNC
→ FINAL VERIFY
→ UPDATE PHASE-LOG
→ COMMIT
→ PUSH
```

# templates/operating/AGENTS.md

# AGENT STRATEGY

`AGENTS.md` is the Layer 3 runtime entry point.

## Startup

Every AI must:

1. read `AGENTS.md`;
2. identify the current phase/task;
3. synchronize the repository;
4. inspect task ownership;
5. read relevant documentation;
6. identify required skills;
7. retrieve relevant memory;
8. construct minimum sufficient context;
9. execute;
10. verify;
11. update state;
12. commit.

## Multi-AI coordination

The project repository may be used by multiple AI agents concurrently.

Before claiming work:

```text
SYNC
→ TASK-LOG
→ dependencies
→ affected files
→ ownership
→ CLAIM
```

An AI must not modify a conflicting task already owned by another AI.

Independent tasks may execute in parallel.

## Agent selection

Use specialist agents when useful:

* Architect
* UI/UX
* Frontend
* Backend
* Database
* Testing
* Security
* DevOps
* Review

Agent switching is allowed when beneficial.

Before switching, persist enough state for the next agent to continue independently.

## Conflict handling

If another AI changes the same area:

```text
STOP
→ SYNC
→ inspect changes
→ preserve work
→ resolve
→ verify
→ continue
```

Never silently overwrite another AI's work.

## Source of truth

Approved project documentation defines intended behavior.

Task/phase logs define execution state.

Git defines repository history.

Memory preserves reusable project knowledge.

Conversation history is not authoritative.
